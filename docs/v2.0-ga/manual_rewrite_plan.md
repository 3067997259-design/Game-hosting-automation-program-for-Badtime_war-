## 三、后半部分的问题

§5.1 正文起到文末约 5.4 万字（作者已改的部分约 8 千字）。逐条对应作者提的四个问题：

**新人看完上不了手**
- 公式先行，变量满屏（A、F、B、L、C_i、W_j、E_effective），没先说“打一下会发生什么”。
- 同一条规则在好几处各说一遍：25% 保底出现在 5 个小节，外甲计费散在 §4.3、§5.2、§5.3、§11.1、§15.1。
- 天赋专属的例外塞在通用规则里。

**AI 查不到规矩**
- 设计记录混进规则：19 处 DEC 编号、14 处“已定”、14 处风洞/校准/验收、11 处 RFC/铁律/钉。
- 数字在正文和 §17 各写一份，改一处另一处就过期。
- 同一个东西有好几个名字，“R1”既指第一轮，又指一轮里判定先攻的阶段。
- 标题是宣传语（“从三个 NPC 到一支军队”“从二十六张牌到三个按钮”），按内容搜不到。

**缺作者特色**
- AI 腔的金句代替了作者的声音：“终焉是毒圈，只是它不画成圈”“你只是从选手席去了证券交易所”。

**语法不通**
- 一句话用分号串五六个分句：这部分共 783 个分号，54 段一段里有 3 个以上；多重否定随处可见，主语常常缺失。

## 四、文风规范

来自作者 10-27 的删改（[完整 diff](../../artifacts/ga-manual/author-edits-2026-10-27.diff)）和对第五章样稿的反馈。重写一律照此执行，以后作者的新改法继续补进来。

### 4.1 删

| 删什么 | 例子（改前 → 改后） |
|---|---|
| AI 金句、排比收尾 | “规则更少，天赋更大，对局更短。”、“家是起点，不是保险箱，更不是终局掩体。” → 删 |
| 设计论证 | “最后这条解决了三件事：残局无躲猫猫死角……” → 删，换成一句作者旁白 |
| 决议编号与日期 | “**外甲底座已定（DEC-003，2026-10-26）**：采用……” → 直接讲外甲是什么 |
| 玩家用不上的实现细节 | “落点使用固定建筑 ID 次序……”、“(BLACK FANG 465)” → 删 |
| 重复解释 | “lock 不再是独立的根行动……” → 删；“‘免费’表示不占 T1……” → 改成一句口语旁白 |

### 4.2 改

| 改法 | 例子 |
|---|---|
| 先说“这是什么”，再说规则 | 外甲：“外层护甲是你可以获得的，用来提高你对应属性防御的道具……它有两个属性：属性防御和耐久。” |
| 术语换成玩家的话 | “演出准备度” → “释放技能需要的资源”；“每未来 R4” → “在 R4 阶段” |
| 用常见的游戏说法，不用生硬的译名 | “直达伤害” → “真实伤害（真伤）”；“形态转折” → “免死”；“出手伤害” → “原始伤害” |
| 用“一般”“需要注意的是”承认例外，不在这里展开 | “一般上限为20”、“一般情况下为每减免 1 点伤害消耗 1 点耐久” |
| 用具体例子讲方向性规则 | 感知：“A和B都有隐身效果，但只有A有探测……” |
| 标题直白，必要时括注常见游戏术语 | “三层防御漏斗” → “防御结算顺序”；“灼烧与重伤” → “灼烧（DoT）与重伤（Debuff）” |
| 表格加“备注”列，放来源或吐槽 | 控制表的备注列 |

### 4.3 加

- 斜体旁白，紧跟在规则后面，讲早期版本怎么样、为什么改：“*在早期版本里，lock和find是占据单独行动的……不然实在是太磨蹭了*”。
- 吐槽、梗、开发者自嘲、桌上故事。**这些由作者自己插入**，见 4.6。
- 没想好的地方老实写 `todo`。

### 4.4 格式

- 一段一行，不在句子中间硬换行。
- 不用加粗短句开头的“说明书”格式；加粗只给第一次出现的关键词（如“第 1 层是**屏障**”）。
- 旁白用斜体单独成行；顺口一句的吐槽用括号。
- 代码块用来画流程（轮次、防御顺序），以及节末的“精确结算（可以跳过）”。精确结算留在正文里当示例。

### 4.5 天赋例外放在哪里

- **只跟一个天赋有关的例外，写在那个天赋的小节里**，例如星野的进阶装备融合、光环、持盾。
- **好几个天赋共用同一个挂点的例外，可以留在通用规则里讲**，并点名目前有谁。例如第 1 层屏障（G3 七重圆环、G7 架盾都挂在这一层）、
  濒死时的免死（G0/G1/G2/G4/G7）、双倍磨损的来源（T1/G0/G7）。
- 通用规则里点了名，以后改这个天赋就得记着回来改，所以拿不准时放天赋小节。
- 改任何一个天赋时，全文搜索它的编号（如“G7”），把通用规则里点名的地方一起改。

### 4.6 旁白分工

| 内容 | 谁写 |
|---|---|
| 规则正文、例子、表格、精确结算 | 助手 |
| “早期版本是怎样的”这类事实旁白 | 助手起草，只写能在仓库历史里核实的；作者可删可改 |
| 玩笑、吐槽、个人感受、天赋台词、天赋选择建议 | 作者自己在合适的位置插入。助手不代写，也不留占位标记 |

## 六、每一节怎么写（助手的步骤与自检）

1. **取来源**：DEC 表相关条目、RFC 对应段、`balance.json` 的 `ga` 块、`engine/ga` 实现和对应测试。
   三者不一致时以“已决 DEC + 已实现且有测试的行为”为准；仍然对不上的，列进“待作者拍板”，不自己挑一个写。
2. **列问题**：这一节要回答玩家的哪些问题（例：我打别人一下掉多少血？我的甲什么时候碎？）。
3. **写**：先说这是什么 → 步骤或表格 → 例子 → 需要注意的例外 → 节末精确结算（需要时）。
4. **自检**：
   - 没有 DEC 编号、日期、“已定”、风洞/校准/验收、RFC/铁律/钉等设计用语；
   - 每个数字和 `ga` 配置一致；每个数字例子都进了算例测试；
   - 用词符合 4.7，新术语进术语表；
   - 天赋例外按 4.5 放置：单个天赋的进天赋小节，共同挂点才留在通用规则；
   - 一条规则只在一处定义，别处只放链接；
   - 一句话一个意思，一段里分号不超过两个，不写多重否定；
   - 没有 AI 金句、排比收尾、拟人化比喻，没有加粗短句开头；
   - 不写玩笑，不留占位标记；旁白只写能核实的早期版本事实。
5. **交付**：章节正文、待作者拍板的问题、测试结果。

## 十一、天赋章节的合作方式

天赋的子效果名字会大量改动，作者也可能在改稿时引入新机制。所以天赋章节按下面的循环推进：

1. **助手写平实版**：照第四节的规范写，每条规则对照引擎核实，数字例子进算例测试。并入手册后存快照：
   `python -B tools/manual_review.py snapshot <标签> --note <说明>`。
2. **作者大改**：在手册里直接改，可以改名、重写、加机制。觉得需要引入新机制时，告诉助手是哪一段。
   改完说一声。
3. **助手审阅**：`python -B tools/manual_review.py diff <标签> --sections <章节>`，报告写在
   `artifacts/ga-manual/reviews/`。报告按小节列出：
   - 规则数字的增删（附上下文）、配置里找不到的数字；
   - 改掉的名字（书名号、加粗、表格里整格换掉的词）以及旧名还出现在手册哪一节、哪份设计稿；
   - 计划 5.1 里必须保留、但没找到的规则；断开的 § 引用；
   - 逐句改动，删掉的标 `[-…-]`，新加的标 `{+…+}`。
4. **助手处理**：
   - 改名：同步手册其他章节（§5.x 的共同挂点、§7.4、§13、§15、§17）、本计划的索引表和规则表；
     设计稿（RFC）里的旧名单独列给作者，问要不要一起改；
   - 数字或规则变了、但作者没说是新机制的：逐条问作者，是笔误还是有意改动；
   - 作者说明了的新机制：记进 GA 文档中心的待办（需要改引擎、改配置的另开任务），
     手册里先按作者的写法保留；
   - 措辞上的改法补进第四节的文风规范；算例测试跟着更新。
5. 下一批平实版可以在作者改稿期间写进单独的草稿，作者改完、助手审完之后再并入手册，不和作者同时改同一个文件。

审阅工具只给提示，不下结论：最后都由助手读逐句改动、对照引擎和配置后判断。
