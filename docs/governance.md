# 文档治理规则

## 1. 目标

本规则用于防止同一机制在多份“权威文件”中同时演化。维护工作遵循：先登记、后拆分；先结构、后语义；先保全、后归档。

## 2. 权威单位

权威单位是“主题 + profile”，不是整份文件。例如 `talents.g2.stage + v2exp` 只能有一个现行定义；同一文件可以覆盖多个主题，但必须在登记表中逐项声明。

事实类型分别由以下信源承担：

| 事实类型 | 首要信源 | 冲突处理 |
|---|---|---|
| 数值 | `data/balance.json` | 文档用 `⟦bal:...⟧` 引用，不复制裸值 |
| 当前实现行为 | 代码与测试 | 与设计不符时登记为实现偏差 |
| 玩家规范 | 已审定手册模块 | 与实现不符时不得静默改文档 |
| 已接受设计 | 决策记录 | 接受后再同步手册与实现 |
| 提案 | RFC/设计草案 | 不具现行规则权威 |
| 历史 | changelog/开发日记 | 只解释演化，不定义现行规则 |

## 3. 文档状态

- `canonical`：在声明的主题和 profile 内为唯一现行规范。
- `candidate`：结构上准备成为权威，但尚未完成语义审计。
- `migration-source`：仅作为迁移内容基线，迁移完成后退役。
- `generated`：由作者源生成，禁止手工编辑。
- `draft`：未接受的设计提案。
- `decision-ledger`：记录决定和待决定事项，本身不直接定义玩法。
- `mixed`：混合现行内容、旧内容或草案，必须拆分后才能取得权威地位。
- `historical`：历史或评论资料。
- `superseded`：已被明确取代，不再参与现行规则解释。
- `scoped-current`：仅在一个工具、子项目或操作范围内有效。

## 4. Profile 纪律

每个规范模块必须声明一个或多个适用 profile。`m9-rfc` 不自动属于 `v2exp`；设计文件中的“已拍板”只表示该 RFC 内部决定，不表示已经进入现行游戏。

## 5. 生成纪律

模块化 Markdown 是迁移完成后的作者源。生成链为：

```text
docs/handbook/**/*.md
        ↓ manifest 顺序装配
完整 Markdown
        ↓ 发布转换
完整 DOCX/PDF
```

生成文件顶部必须有“禁止手工编辑”标记。生成检查必须验证装配结果、链接和 `balance` 占位；生成文件发生人工漂移时检查失败。

## 6. 拆分纪律

1. 结构拆分期间不得修正机制、数值或措辞。
2. 每批修改不超过五个文件。
3. 拆分后对模块正文回组装，并与迁移基线的逻辑文本比较。
4. 导航、元数据和生成标记不属于原正文，可在比较时明确排除。
5. 同一规则只在一个模块定义；摘要必须链接到完整规则。

## 7. 冲突处理

每个冲突写入 `contradictions.md`，至少包含：编号、主题、profile、证据、影响、建议处理、是否需要用户拍板和状态。允许的结论只有：

- 文档过时；
- 实现偏差；
- profile 分叉；
- 草案尚未转正；
- 需要设计决定；
- 误报或无需处理。

不得以“修改日期最新”“文件名最正式”或“代码目前如此”为唯一理由自动消解规范冲突。

## 8. 归档与删除

只有当替代文档已登记、所有现行链接已更新、独有内容已迁移并通过检查后，旧文件才能标记 `superseded` 或移动到历史区。删除必须另行确认；初步维护阶段不删除文稿。
